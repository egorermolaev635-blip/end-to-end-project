# Week 13. ML-блок: поиск аномалий температуры

## Выбранный сценарий

Выбран вариант B — аномалии. В проекте есть погодные данные Open-Meteo по Новосибирску, но нет готовой целевой переменной `target`, поэтому supervised-модель была бы искусственной.

## Данные

- Источник: `data/normalized/variant_03/2026-03-08_21-33-20.csv`
- Гранулярность: 1 строка = 1 час наблюдения
- Количество строк: 48
- Анализируемая метрика: `temperature`

## Метод

Использован простой IQR-метод:

- Q1 = -1.42
- Q3 = -0.20
- IQR = 1.22
- Нижняя граница = -3.26
- Верхняя граница = 1.64

Точка считается аномалией, если температура ниже нижней границы или выше верхней границы.

## Результат

- Найдено аномалий: 1 из 48 (2.08%)
- Самая выраженная аномалия: 2026-03-09 23:00:00 — -4.1 C.
- Таблица аномалий: `docs/ml/anomalies_top.csv`
- График: `docs/ml/metrics.png`

## Интерпретация

Найденная точка похожа на резкое похолодание в конце периода. По текущим данным это скорее погодное событие, а не ошибка формата данных: значение числовое, дата корректная, пропусков нет.

## Leakage и честность оценки

Target в признаки не добавлялся, потому что target отсутствует. Для этой недели выбран не supervised ML, а прозрачная эвристика. Если делать production-версию, границы IQR лучше подбирать на историческом train-периоде и проверять на более позднем test-периоде, чтобы не подглядывать в будущие данные.

## Вывод

Метод полезен как простой мониторинг: он быстро показывает подозрительные часы в температурном ряду. Для надежной аналитики нужно больше дней данных и сравнение с соседними днями или климатической нормой.
