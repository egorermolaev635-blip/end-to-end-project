- используется поле: `date`
- определяется как максимальная дата в mart
- обновляется после успешного выполнения всех этапов

Пример:
watermark = 2026-04-14

---

### Business key

Одна строка витрины = один день по одному городу

Business key:

---

### Идемпотентность

- повторный запуск пайплайна не изменяет результат при одинаковых входных данных
- загрузка в PostgreSQL выполняется через `if_exists="replace"`
- дубликаты не накапливаются

#### Full

- выполняются все этапы заново
- все слои пересоздаются
- витрина полностью пересобирается
- таблица в БД заменяется

#### Incremental

- используется `state.json`
- сохраняется и используется watermark
- пайплайн можно безопасно запускать повторно
- результат не дублируется

### Docker Compose

Файл:
`docker-compose.yml`

В compose-файле описаны два сервиса:

| Сервис | Назначение |
|--------|------------|
| `postgres` | база данных PostgreSQL для хранения mart-витрины |
| `metabase` | BI-инструмент для построения дашборда |

---

### Volumes

В проекте используются два volume:

| Volume | Назначение |
|--------|------------|
| `pgdata` | хранит данные PostgreSQL |
| `metabase_data` | хранит настройки и дашборды Metabase |

## Обоснование выбора варианта

Вариант A требует target и честного train/test split. В проекте есть погодный временной ряд, но нет готовой целевой переменной.

Чтобы не создавать искусственную модель, выбран вариант B:

```text
анализ метрики → поиск выбросов → таблица аномалий → график → вывод
```

Такой подход лучше соответствует текущему состоянию данных.

## Метод

Использован IQR:

```text
Q1 = 25-й процентиль
Q3 = 75-й процентиль
IQR = Q3 - Q1
lower_bound = Q1 - 1.5 * IQR
upper_bound = Q3 + 1.5 * IQR
```

Аномалия — это точка, где `temperature` ниже нижней границы или выше верхней границы.
